# Computational capability inventory

Reviewed 14 November 2026 against the current source tree, documentation, and selected supplied questions. This is an implementation backlog and status assessment. It does not add an extractor or executor.

The system needs reusable capabilities that compose into answers. A question such as "Which floor has the largest total bedroom area, excluding balconies?" combines scope resolution, room classification, area acquisition, exclusions, grouping, summation, and ranking. It should not require a dedicated model for that sentence.

The backend [Nemotron adapter](nvidia_info.md) now supports sync/async text,
local-image, and validated JSON calls, plus usage reporting and a connection-check
CLI. Its HTTP tests use mocked responses; separate live text and synthetic
image/JSON requests passed. The [IFC question API](IFC_QUESTIONS.md) now connects
bounded plan compilation to the local executor and frontend evidence panel.
Drawing perception accuracy and complete IFC-family coverage remain unverified.

Current implementation includes the shared contracts and validation, a [local IFC extractor and query executor](IFC_ENGINE.md), and an [import/viewing workbench](../frontend/README.md). IFC questions use bounded Nemotron plans, CPU execution, native topology and source evidence; natural-language summaries are generated deterministically from executed values. The frontend provides IFC 3D inspection and answer highlights. Synthetic 2D sources remain offline fixtures, while imported image/PDF questions return unverified candidate regions. [dataset_audit.py](../dataset/dataset_audit.py) supplies dataset/file/STEP-record/SVG inspection. A [one-image Nemotron door-labeling pilot](../experiments/door_labeling/RESULTS.md) saves provisional boxes and a separate assistant review. General detection inventories, database persistence and metric geometry computation remain gaps. Contract/frontend fixtures are synthetic; selected real-model checks do not establish dataset-wide accuracy.

[DXF import and layout previews](DXF_PREVIEW.md) now feed the same unverified
image-candidate flow. This is rendering support; native CAD fact extraction,
logical object inventories and geometric query execution remain gaps in E01/E04/E05.

Organizer clarification reported on 14 November: prioritize questions about the drawing/view shown. Broader capabilities below are a backlog, not a requirement to enable every operation for every source. Preserve explicit model-wide scope in existing reference questions.

The [project scope](PROJECT_SCOPE.md) is the supplied dataset and its demonstrated
question families. Working for that set is sufficient; unknown evaluation classes
are not a requirement. This inventory mixes capabilities needed by supplied
questions with possible extensions. Required work must trace to those questions;
an unimplemented extension does not block acceptance. Known dataset tasks remain
required even when their implementation is difficult or their row count is small.

Status terms below distinguish different kinds of progress:

- **Implemented:** the specified component executes the described behavior. A mock UI or standalone executor does not establish their integration.
- **Validation implemented:** code checks a supplied record or relationship. This does not mean it extracts the record or answers a question.
- **Contract defined:** the schema can represent the inputs, operation, or result; execution still needs implementation.
- **Sample documented:** existing repo reports describe checks on real source examples; this is not a reusable implementation or a dataset-wide accuracy result.
- **Recommended:** an existing document proposes the approach or tool; no integrated implementation was found.
- **Gap:** the current operation set or implementation does not provide the capability directly.

Area deserves an explicit distinction because it can mean several different capabilities. **Lookup** returns a source area with the requested definition. **Calculation** measures established physical geometry. **Estimation** first infers boundaries or scale and must retain that qualification. These methods can disagree because of both extraction errors and different net/gross definitions.

For a simple polygon with holes, calculate `area(shell) - sum(area(holes))`. For a uniform image scale `s` in metres per pixel, physical area is `pixel_area * s * s`. For multiple included regions, measure their union when overlaps would otherwise be counted twice, then apply the defined exclusions. A rough 1% scale error alone contributes roughly 2% area error before boundary errors. Store the calibration, polygon, holes, exclusions, basis, and conversion alongside the result.

The repo already documents a Swiss example with shell area 48.070375 m2 and two column holes; subtracting them gives 47.945139 m2, rounding to reference 47.95. It also documents a not-to-scale raster plan. Those examples show why an area routine must check both topology and physical calibration.

The [geometry contract](SCHEMA.md#geometry-and-measurement) documents the validator's limited simple planar 2D checks for zero-area/self-intersecting rings, holes outside shells, and overlapping holes. These checks do not construct room geometry, validate arbitrary 3D topology, or recompute claimed measurements.

A practical build sequence is:

1. **One complete structured-data path:** E01/E04/E08/E09/E10, Q01/Q02/Q04/Q05/Q06/Q13/Q20, and T01/T04. Demonstrate a real count and a room-area answer with exact source evidence, including a scope change and missing-information case.
2. **Raster coverage early:** E02/E03/E05/E06/E07, tile deduplication, and held-out exact-count/localization evaluation within the supplied families. CubiCasa and Swiss account for 96.89% of supplied QA rows; use that to prioritize coverage, not to discard the remaining known tasks.
3. **Broader quantities and schedules:** Q03/Q07/Q08/Q09/Q10/Q11/Q12/Q14, adding only the semantics and geometry the chosen examples require. Treat money, row-wise arithmetic, and surface-area semantics as explicit gaps.
4. **Known topology and specialized questions:** Q15/Q16, then the supplied Q17/Q18 route/rule cases with their actual evidence and limitations. Q19 revision comparison is an optional product extension unless a supplied question requires it; do not implement it in anticipation of a new evaluation class.

The [supplied Nemotron configuration](nvidia_info.md) is the first integration
candidate for plan compilation, multilingual interpretation, and selected crop
interpretation. Verify access and structured-output/image behavior before using
